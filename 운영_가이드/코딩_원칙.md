# Claude Code 코딩 원칙

> **이 문서의 위치**: 4가지 보편 원칙(Karpathy 발) × 6개월 운영 누적 하네스(STEP 0~3·검증 하네스·세션 종료)를 통합한 **운영 철학 레이어**.
> 스킬·구축 가이드는 "어떻게 설치하고 굴리는가"를 다루고, 이 문서는 **"코드를 쓸 때 어떤 자세로 임할 것인가"**를 다룬다.
>
> 진입점 우선순위: `~/.claude/CLAUDE.md` → `<project>/CLAUDE.md` → 본 문서.
> 충돌 시 **더 제한적인 규칙**이 우선한다.

|---|------|-----------|

## 원칙 1 — Think Before Coding (사고 먼저)

> **가정하지 마라. 혼란을 숨기지 마라. 트레이드오프를 표면화하라.**

### 코드 작성 전 의무 절차

- 가정은 **명시적으로 진술**한다. 불확실하면 즉시 질문한다.
- 해석이 둘 이상 가능하면 **모두 제시**한다 — 혼자 결정하지 않는다.
- 더 단순한 접근이 있으면 말한다. 합당한 근거가 있으면 사용자 의견에 반대해도 된다.
- 무언가 불명확하면 **멈춘다**. 무엇이 헷갈리는지 이름을 붙이고 묻는다.

### 체크 — 이 원칙을 지켰는가

- [ ] 요청을 받자마자 코드부터 쓰지 않았다
- [ ] 작업 영역(프로젝트별 도메인 표 기준)을 명확히 했다
- [ ] HANDOFF_NOW.md 또는 진입 문서를 먼저 읽었다
- [ ] 모호한 요구사항은 추정이 아니라 질문으로 해소했다
- [ ] 계획을 사용자에게 보여 확인을 받았다

## 원칙 2 — Simplicity First (단순함 우선)

> **문제를 해결하는 최소한의 코드. 추측성은 없다.**

### 금지 사항

- 요청되지 않은 기능 추가 금지.
- 일회성 코드에 대한 추상화 금지.
- 요청되지 않은 "유연성"·"설정 가능성" 금지.
- 발생 불가능한 시나리오에 대한 에러 처리 금지.
- 200줄로 쓴 코드가 50줄로 가능하다면 **다시 써라**.

스스로에게 던질 질문: **"시니어 엔지니어가 이걸 보고 과설계라고 할까?"** 그렇다면 단순화한다.

### 추가 디테일

- 버그 수정에 주변 정리 금지. 일회성 작업에 헬퍼 함수 금지. 가상의 미래 요구를 위한 설계 금지.
- 비슷한 줄 3개 정도는 **선부 추상화보다 낫다**.
- 내부 코드와 프레임워크 보장은 신뢰하라. 검증은 **시스템 경계**(사용자 입력·외부 API)에서만.
- 절반만 구현된 코드 금지 — 끝까지 작동하지 않으면 시작하지 마라.
- 주석은 기본적으로 쓰지 않는다. **WHY가 자명하지 않을 때만** 한 줄 주석을 추가한다 (숨겨진 제약·미묘한 불변·특정 버그 우회). WHAT은 식별자 이름으로 표현한다.

### 체크 — 이 원칙을 지켰는가

- [ ] 요청 범위를 벗어난 기능을 추가하지 않았다
- [ ] 한 번만 쓰는 코드에 클래스·인터페이스를 만들지 않았다
- [ ] 미래의 가상 요구를 위한 옵션·플래그를 만들지 않았다
- [ ] "이 케이스가 발생할 수 있나?"를 자문하고 불가능한 케이스의 방어 코드를 제거했다
- [ ] 코드 라인 수를 한 번 더 줄여봤다

## 원칙 3 — Surgical Changes (외과적 변경)

> **꼭 손대야 하는 곳만 만져라. 네가 만든 흔적만 정리하라.**

### 기존 코드 편집 시

- 인접한 코드·주석·포맷팅을 "개선"하지 마라.
- 망가지지 않은 것을 리팩토링하지 마라.
- 네가 다르게 짰을 코드라도 **기존 스타일에 맞춰라**.
- 무관한 dead code를 발견하면 **삭제하지 말고 언급만** 한다.

### 변경이 고아 코드를 만들었다면

- 네 변경 때문에 사용되지 않게 된 import·변수·함수만 제거한다.
- 사전 존재한 dead code는 **요청 없이는 건드리지 않는다**.

### 테스트

> **모든 변경된 줄은 사용자 요청에 직접 추적 가능해야 한다.**

### 체크 — 이 원칙을 지켰는가

- [ ] 변경된 줄마다 "왜 이 줄이 필요한가?"에 사용자 요청으로 답할 수 있다
- [ ] 인접 코드의 포맷팅·주석을 임의로 정리하지 않았다
- [ ] 기존 코드 스타일·패턴(API 레이어·상태 관리·컴포넌트 구조)을 따랐다
- [ ] 무관한 dead code는 삭제 대신 언급으로 처리했다
- [ ] 내 변경으로 생긴 미사용 import만 정리하고 사전 존재 dead code는 그대로 뒀다

## 원칙 4 — Goal-Driven Execution (목표 기반 실행)

> **성공 기준을 정의하라. 검증할 때까지 루프를 돌려라.**

### 작업을 검증 가능한 목표로 변환

| 모호한 요청 | 검증 가능한 목표 |
|---|---|
| "유효성 검증 추가" | 잘못된 입력에 대한 테스트를 작성하고 통과시킨다 |
| "버그 고쳐" | 버그를 재현하는 테스트를 작성하고 통과시킨다 |
| "X 리팩토링" | 리팩토링 전후 모두 테스트가 통과함을 보장한다 |

다단계 작업의 경우 **단계와 검증 체크포인트**가 있는 짧은 계획을 진술한다.

### 테스트 작성 기준

| 변경 유형 | 테스트 |
|---|---|
| 버그 수정 | **필수** — 재현 테스트 먼저, 통과시키기 |
| 새 비즈니스 로직 함수·훅 | **필수** |
| UI 컴포넌트만 변경 | 선택 |
| 문서·설정만 변경 | 생략 |

범위 불명확 시 `test-writer` 에이전트 호출 (프롬프트에 **"기존 소스 파일 수정 금지, 테스트 파일만 작성"** 명시 필수).

> 검증 하네스 체크리스트·빌드/타입/린트 디버깅 루프·UI 검증·HANDOFF 갱신 절차는 §관련 문서 참조.

### 체크 — 이 원칙을 지켰는가

- [ ] 작업 시작 전 "성공이란 무엇인가?"를 한 문장으로 정의했다
- [ ] 버그 수정·새 비즈니스 로직에 테스트가 있고 모두 통과한다
- [ ] UI 변경이라면 브라우저에서 직접 동작을 확인했거나, 못한 사실을 명시했다
- [ ] 빌드·타입·린트가 모두 통과한다 (또는 2회 실패 시 즉시 보고했다)
- [ ] HANDOFF 3종 갱신 + 작업 결과 요약을 출력했다

## 4원칙 통합 흐름 (요청 수신 → 세션 종료)

```
[요청 수신]
   ↓
원칙 1: 작업 영역 판별 → 진입 문서 로드 → 모호하면 질문
   ↓
원칙 1: 기존 코드 분석 (유사 파일 ≥2) → 구현 계획 제시 → 사용자 확인
   ↓
원칙 4: 성공 기준 정의 (검증 가능한 목표로 변환)
   ↓
[코드 작성]
   ↓
원칙 2: 요청된 만큼만 — 추상화·미래 대비·과한 에러 처리 금지
원칙 3: 변경 줄 = 요청 추적 가능 — 인접 코드 임의 정리 금지
   ↓
[검증]
   ↓
원칙 4: STEP 2 체크리스트 → 테스트 → 빌드/타입/린트 → UI 확인
   ↓
[세션 종료]
   ↓
원칙 4: HANDOFF 3종 갱신 + 작업 결과 요약
```

## 원칙 위반의 대표 패턴 (실패 모드)

| 위반 | 흔한 모습 | 결과 |
|------|----------|------|
| 1번 위반 | "어차피 X 영역일 거야"라며 추정으로 시작 | 엉뚱한 영역 수정 → 롤백 |
| 1번 위반 | 모호한 요구사항을 그대로 받아 구현 | 의도와 다른 결과 → 재작업 |
| 2번 위반 | "나중에 쓸 수도 있으니까"로 옵션 추가 | 죽은 코드 + 유지보수 비용 |
| 2번 위반 | "혹시 모르니까" try/catch로 감싸기 | 진짜 에러를 숨김 |
| 3번 위반 | 버그 수정하면서 주변 포맷팅·이름 정리 | diff 노이즈 + 리뷰 부담 |
| 3번 위반 | 기존 패턴 무시하고 "더 나은" 방식으로 다시 작성 | 일관성 파괴 |
| 4번 위반 | "되는 것 같다"로 완료 처리 | 회귀·잠복 버그 |
| 4번 위반 | UI 수정 후 브라우저 확인 생략 | 실제로는 깨진 화면 |
| 4번 위반 | HANDOFF 갱신 없이 세션 종료 | 다음 세션 컨텍스트 단절 |
