## 🔴 STEP 0 — 작업 시작 전 필수 (건너뜀 금지)

### 0-A. 작업 영역 판별

요청을 받으면 **코드를 건드리기 전에** 작업 대상 영역을 판별한다.
불명확하면 **반드시 사용자에게 먼저 질문한다.** 임의 추정 금지.

<!-- FILL: 프로젝트의 실제 작업 영역·키워드로 테이블 수정

  [작성 방법]
  1. package.json의 `workspaces` 키 또는 apps/ 디렉토리 1단계 목록 확인
  2. 각 패키지(디렉토리)의 역할을 키워드로 추출
  3. 한 행 = 한 패키지. 키워드는 사용자가 자연어로 말할 때 쓸 법한 단어들

  [단일 앱 예시]
  | 채팅, 메시지, 스트림 | `src/` |
  | API, 서버, 인증 | 백엔드 |

  [모노레포 예시]
  | 포털, 채팅, <서비스명> | `<서비스명>/` |
  | 관리자, admin | `<서비스명>/` |
  | API, 백엔드, FastAPI | `services/` |
-->

| 키워드 / 단서 | 작업 영역 |
|---|---|
| `[키워드1]`, `[키워드2]` | `[패키지경로1]` |
| `[키워드3]`, `[키워드4]` | `[패키지경로2]` |
| API, 백엔드, Python, DB | 백엔드 서비스 |
| Docker, CI/CD, 공통 설정 | 루트/공통 |

불명확 시 질문:
> "이 작업은 [패키지1], [패키지2], 백엔드 중 어느 쪽인가요?"

---

### 0-C. 기존 코드 분석 (코드 작성 전 필수)

유사 기능 파일 **최소 2개 이상** 확인: 경로·컴포넌트 구조·API 호출·상태 관리 방식 파악.
버그 수정 시 생성 화면 vs 수정 화면 동일 기능 구현체 비교 필수.

### 0-D. 구현 계획 수립 및 확인

분석 결과를 바탕으로 단계별 구현 계획을 수립한 뒤 **사용자에게 제시하고 확인을 받는다.**

```
[구현 계획]
- 수정 대상: <파일 목록>
- 변경 내용: <단계별 작업>
- 영향 범위: <영향받는 기능>
```

**사용자 확인 전까지 코드 작성·파일 수정 금지.**
계획 변경 요청 시 계획을 수정한 뒤 재확인한다.

## 에이전트 작업 방식 (필수)

<!-- FILL: 프로젝트 특성에 따라 단계 설명 보완 가능. 기본 5단계 루프는 공통 적용. -->

**모든 작업에서 아래 루프를 따른다. 임의 실행 금지.**

```
1. 분석 — 현재 상태·문제를 파악하고 다음에 할 일을 결정
   → 유사 기능 파일 최소 2개 이상 확인 (경로·컴포넌트 구조·API 호출·상태 관리 방식)
   → 버그 수정 시 생성 화면 vs 수정 화면 동일 기능 구현체 비교 필수
2. 제안 — "다음 행동: [구체적 행동]을 하겠습니다. 진행할까요?" 형태로 사용자에게 먼저 물어봄
3. 대기 — 사용자 승인(예/진행/ok 등) 확인
4. 실행 — 승인 후에만 코드 작성·파일 수정·명령 실행
5. 보고 — 완료 결과 요약 후 다음 행동 제안으로 돌아감
```

**예외 — 승인 없이 바로 실행 가능한 것:**
- 파일 읽기·검색 등 조회성 작업
- 사용자가 "바로 해줘" / "한 번에 다 해줘" 등으로 명시적으로 허가한 경우

## 🔴 STEP 1 — 작업 중 강제 규칙

<!-- FILL: 프로젝트 아키텍처 분석 후 규칙 추가·수정
  분석 기준:
  - API 레이어 패턴: 컴포넌트에서 직접 fetch? 별도 api/ 레이어?
  - 상태 관리: Redux / Zustand / React Query / 서버 상태?
  - 다른 패키지 참조 의존성 (한 서비스가 다른 서비스 소스를 참조해야 하는 경우)
  - 금지 사항: gitignore된 파일 임의 수정, 환경변수 하드코딩 등
-->

> **규칙 위반 발견 시: 즉시 중단 → 사용자에게 위반 내용 보고 → 지시 후 재개. 임의 수정 후 계속 진행 금지.**

| 규칙 | 위반 시 |
|---|---|
| **[패키지명]: 컴포넌트에서 직접 API 호출 금지** | 즉시 중단 → 사용자 보고 → 지시 후 수정 |
| **이슈 번호 없이 커밋 금지** | 즉시 중단 → 사용자 보고 → 이슈 생성 후 재개 |
| **[develop/main]에 직접 커밋 금지** | 즉시 중단 → 사용자 보고 후 브랜치 생성 |
| **커밋은 명시적 요청 시에만** | 사용자가 "커밋해줘" 전까지 커밋 불가 |

<!-- FILL: 패키지 간 의존성 규칙이 있으면 추가
  예: 한 서비스가 다른 서비스 소스를 참조해야 하는 경우
-->

> **규칙 우선순위**: 패키지별 CLAUDE.md가 있으면 그것이 우선. 충돌 시 **더 제한적인 것** 적용.

## 🔴 STEP 2 — 검증 하네스 (코드 작성 후 필수)

```
[규칙 준수 체크]
- [ ] 기존 파일 구조 준수
- [ ] API 레이어 패턴 준수
- [ ] 상태 관리 방식 일치
- [ ] 기존 코드 스타일 일치
- [ ] 테스트 작성 여부 확인
```

<!-- FILL: 프로젝트별 추가 체크 항목
  예: disabled 패턴 사용 (조건부 언마운트 없음)
  예: 특정 주석 보존 규칙
  예: 환경변수 prefix 규칙
-->

**체크 실패 시:** 위반 항목을 사용자에게 보고한 뒤 수정 방향을 확인받는다. 스스로 판단해 수정 후 완료 처리 금지.

**테스트 작성 기준:** 버그 수정·새 비즈니스 로직 함수·훅 → **필수** / UI 컴포넌트만 변경 → 선택 / 문서·설정만 변경 → 생략.

**UI 변경 검증 방법 (완료 처리 전 확인):**
UI·화면 변경이 포함된 경우, 완료 처리 전 반드시 아래 질문을 한다:

> "UI 변경이 포함되어 있습니다. 검증을 어떻게 진행할까요?
> 1. Playwright 에이전트 자동 검증
> 2. 직접 확인하겠습니다"

- **1 선택** → `webapp-testing` 스킬로 `UI_검증_전략.md` 3단계 기준 실행
- **2 선택** → 완료 처리. 개발자가 직접 검증

**빌드·타입·린트 오류 시:** ① 내 코드 문제 → 즉시 수정 ② 기존 호환성 문제 → `debugger` 에이전트 ③ 2회 이상 반복 실패 → **즉시 중단·사용자 보고**

## 🔴 STEP 3 — 세션 종료 강제 절차

코드·문서 변경이 있었던 세션은 사용자 지시 없이도 자동 수행한다.

<!-- FILL: 각 패키지별 docs 경로로 수정
  기본 패턴:
  - HANDOFF_NOW: `[패키지경로]/docs/status/HANDOFF_NOW.md`
  - 세션_노트: `[패키지경로]/docs/history/세션_노트.md`
  - HANDOFF: `[패키지경로]/docs/plans/HANDOFF.md`
-->

**[패키지1] — 갱신 순서 (순서 바꾸지 말 것):**
1. `[패키지1경로]/docs/status/HANDOFF_NOW.md` — §1 현재 상태·§2 다음 작업 갱신 (60줄 이하 유지)
2. `[패키지1경로]/docs/history/세션_노트.md` — 최상단 prepend (`> Session note YYYY-MM-DD: [요약]`)
3. `[패키지1경로]/docs/plans/HANDOFF.md` — `## Session Update YYYY-MM-DD` 섹션 최상단 추가

**갱신 후 일관성 검증:** HANDOFF_NOW.md §2 첫 항목이 최신 다음 작업인지 확인 / HANDOFF_NOW.md 60줄 이하.

**공통 — 변경 결과 요약 출력:**
```
[작업 결과]
- 변경 파일:
- 주요 변경:
- 영향 범위:
```

위 결과 요약 없으면 작업 완료로 간주하지 않음.

## 협의 대기 상태 처리

협의가 필요해 진행 불가 시: ① 즉시 중단 ② HANDOFF_NOW.md §2에 `⏸ [협의 대기] <작업명> — <협의 내용> / 담당: <팀원명>` 추가 ③ 사용자에게 보고 ④ 독립적인 다른 태스크로 전환.

## 작업 범위 초과 시

요청 범위 밖 변경(파일·디렉토리 추가, 의존성 설치, 설정 수정, 요청하지 않은 파일 수정 등)이 필요하다고 판단될 때:
① 즉시 중단 ② 사용자에게 필요한 추가 변경과 이유를 보고 ③ 허가 후 진행.
거부 시 해당 변경 없이 가능한 범위만 구현 후 보고.
