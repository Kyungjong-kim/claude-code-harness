# Examples — 하네스의 진화 흐름

> **초기 부트스트랩과 6개월 운영 후의 격차**를 보여주는 자료.
> `/project-init`이 만들어주는 건 골격이고, 도메인 특정 규칙은 운영하며 누적된다.

---

## 읽는 순서

### 진화 흐름 (1인 운영, M0 → M7)

1. **`01-initial.md`** — `/project-init` 직후 산출물 (~95줄)
   - 4원칙 + 기본 STEP 0~3 골격
   - 도메인 표 빈 자리·강제 규칙 거의 없음
   - 빈 자리가 *의도된* 상태
2. **`02-after-1-month.md`** — 1개월 운영 후 (~110줄)
   - 첫 함정 발견 → STEP 1 강제 규칙 1건 추가 (axios 직접 호출 금지)
   - 2영역 도메인 분기 시작
   - "발견 시점" 컬럼으로 누적 추적 시작
   - 세션_노트 prepend 절차 도입 (회고 회수 비용 해소)
3. **`03-after-6-months.md`** — 6개월 운영 후 (~230줄)
   - STEP 0~3 완전 정착
   - 6영역 도메인 분기 완성
   - 7건의 도메인 특정 강제 규칙 (M0~M5)
   - 서브에이전트 호출 규칙 정착 (worktree 기본·병렬은 명시 요청 시만)
   - §진화 이력 섹션 M0~M7 narrative 포함
   - M7 다이어트 단계 — 공통 패턴 외부 분리 + caveman 압축 프롬프트

### 팀 공유 패턴 (별도 트랙)

4. **`04-team.md`** — 2~5인 팀 하네스 공유 패턴
   - `--local` 모드 설치 + `.claude/skills/` 레포 동기화
   - HANDOFF_NOW.md를 팀 비동기 소통 도구로 활용
   - hooks-config.sh 공유 패턴
   - 1인 운영과 독립적인 보조 시나리오

---

## 핵심 포인트

01 → 02 → 03 세 파일을 순서대로 읽으면 **하네스가 어떻게 누적되는지** 자명하게 보인다.

- 01의 빈 자리들이 02·03에서 채워지는 패턴 관찰
- 02·03의 모든 강제 규칙에 "발견 시점" 표기 — 이게 부트스트랩 출력이 아니라 운영의 결과물임을 증명
- 03 §진화 이력 표 — 각 M0~M7 단계에서 무엇이 어떤 사고/회수 비용 후 추가됐는지 명시
- 03은 본인 6개월 운영 사례를 마스킹·일반화한 것 — 패턴·구조·강제 규칙은 실제 운영 그대로

**부트스트랩 직후 03 수준을 기대하면 실망한다.** 그건 운영의 결과물이지 부트스트랩 출력이 아니다.

---

## 진화 흐름 정합 정보

진화 표(03 §진화 이력)와 실제 파일 줄 수 정합:

| 단계 | 진화 표 줄 수 | 실측 파일 | 실측 줄 수 |
|---|---|---|---|
| M0 (부트스트랩) | ~95줄 | `01-initial.md` | 96줄 |
| M1 (1개월) | ~110줄 | `02-after-1-month.md` | 112줄 |
| M7 (현재, 다이어트 후) | 루트 ~170줄 + 베이스 문서 분리 | `03-after-6-months.md` | 230줄 (다이어트 전 상태 보존을 위해 풀 본문 유지) |

> **03이 다이어트 후 170줄이 아닌 이유**: 외부 사용자에게 진화의 결과(어떤 규칙·이력이 누적됐는지)를 보여주려면 다이어트 전 풀 본문이 더 유용. 실제 운영에선 §진화 이력의 M7 인사이트대로 베이스 문서 분리·자식 압축으로 토큰 절감 적용.

## 검증 시나리오 (사용자가 자신의 진화 추적용)

본인 프로젝트에 하네스 적용 후, 매월 말 다음 점검:

- [ ] `CLAUDE.md` 줄 수가 늘어났나? (안 늘었으면 운영 누적 안 된 신호)
- [ ] STEP 1 강제 규칙이 추가됐나? (안 추가됐으면 함정 미발견 또는 미기록)
- [ ] 작업 영역 표가 더 구체화됐나?
- [ ] 검증 하네스 체크리스트에 도메인 항목 추가됐나?

3개월 후 본인 `CLAUDE.md`를 `examples/02-after-1-month.md`와 비교하면 자기 운영 강도 자명.

## 마스킹 안내

가상 회사 **Acme**의 가상 제품 **Acme Platform** 운영 사례. 6영역:
- `user-portal` — 사용자 포털
- `admin-app` — 관리자 도구
- `user-app` — 사용자 앱
- `AgentService` — 에이전트 서비스 (백엔드)
- 백엔드 서비스 — FastAPI·Python·DB 작업
- 루트/공통 — Docker·CI/CD·모노레포 공통 설정

구체 도메인명·시스템명은 일반 예시로 교체했지만, **패턴·구조·강제 규칙은 실제 운영 그대로**.
